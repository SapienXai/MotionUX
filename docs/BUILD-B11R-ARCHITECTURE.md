# B11R execution design

Baseline is main 606ce55. Its source resolver recognizes eight APIs and its graph compiler emits a shared page shell with four predefined operations. The provider modules are real, but the model cannot author the application's executable implementation.

B11R introduces a separately versioned code project. Legacy B10 documents and B11 graphs retain their existing renderer. New Create app requests extract intent, inspect the prepared inventory, select compatible pinned closures, then receive whole source modules and public APIs for application-specific TSX/CSS generation. The generated application owns its shell, routes, state and component composition.

The host validates emitted paths, syntax, imports, assets, source usage and artifact hashes. Fixed compiler code writes only the accepted managed tree. Next builds and browser interactions run on the isolated host. Up to two bounded module patches consume real diagnostics and preserve unchanged files. Hash-identified attempt traces stay in the private vault. The editor changes declared control values and exact-revision code, keeping previous revisions for recovery. Export uses the same verified modules and pinned lock, with provider notices.

Acceptance follows inventory, a native vertical slice, five normal brief submissions, source interactions and generated code review, independent exports, security and regression. Physical mobile and assistive technology evidence remain separate. The R1–R12 report records gaps explicitly.

## Executable path

`Create app → intent → Brain retrieval → full API/source inspection → suitability selection → authored modules → static validation → isolated Next build → browser journeys → bounded repair → managed revision`

`code-catalog.ts` reads all 500 prepared records. The current dependency profile admits 261 closures and records a reason for each of the other 239. Eligibility describes compiler compatibility. It does not certify visual quality across those 261 components. Selection compares the candidate's actual API with the requested interaction and receives the complete selected implementation. Runtime exports and type declarations have separate metadata. A named default function exposes the default export only.

`code-project.ts` owns the versioned module, route, editable-control, source-usage and journey contracts. `code-validator.ts` checks the local import tree and actual source bindings. `code-program.ts` supplies the trusted routing, persistence, lockfile and control-message wrapper. Application modules own their composition and responsive CSS. The legacy `source-tree.ts` and its fixed synthesis operations remain available to existing documents.

## Editor capability map

| Project | Canonical representation | Editable surface | Run and export |
| --- | --- | --- | --- |
| Owned block document | Typed block document | Existing Puck Canvas, blocks, sections, records and responsive overrides | Existing block compiler |
| Legacy B11 graph | Versioned SourceGraph | Its existing graph controls | Preserved legacy graph compiler |
| B11R code project | Bounded TSX/TS/CSS files, typed controls and source pins | Declared content, color, spacing, size and motion props, Undo/Redo, recoverable drafts, native module revisions | Same authored modules and saved document digest |

The code-project Canvas runs the actual application in its isolated iframe. Desktop, tablet and mobile presets set the iframe's CSS viewport to 1440, 768 and 390 pixels, then scale its presentation to fit the panel. Device changes retain the mounted application's state. A border belongs to the outer frame so it cannot consume the declared viewport width. Draft controls update the live application through the exact-origin, saved-digest envelope. Save creates a new revision before Run or ZIP export.

Arbitrary TSX drag/drop and arbitrary visual property extraction are unsupported. Native revisions can change executable modules after a brief, then run the same compiler and browser gates. They preserve unchanged files, exact source pins and user-edited control values. There is no fixture-domain renderer in this path.

## Source evidence

Source manifests separate the upstream hash, prepared registry hash and compiler import/type adaptations. A prepared file with changed bytes is disclosed as source-adapted. Correcting this derived label does not invalidate an otherwise exact technical pin. Revision, URL, entry, closure, license and source bytes remain checked.

The local reference test reads the actual pin's Git blob from the cached official repository and verifies its upstream hash. It runs that raw TSX through an independent Vite reference with matched app inputs, Next CSS, fonts and assets. Runtime code must match after import and type normalization. Screenshots, accessible output and interaction endpoints compare that reference with the installed Next app. CardStack additionally has a sampled drag trajectory. This is a matched integration reference. Official provider-site page styling has its own context.

Failed generation retains a hash-identified candidate in the private vault. Retry restores its technical source pins and exact saved revision, verifies the candidate first, then spends a bounded repair only when diagnostics require it. A failed candidate never replaces the saved project.
